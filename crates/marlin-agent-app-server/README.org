* Placement

=marlin-agent-app-server= exposes Marlin's Session messages to desktop,
mobile and other external applications. A native client can use its own UI
framework, such as GPUI, and a generated gRPC client over HTTP/2. Rust
applications can enable =grpc= with default features off on =marlin-agent-ui=
and import the client from =marlin_agent_ui::grpc::v1=. Standalone hosts can enable
=grpc= on this package or =app-server= on Agent CORE. The TUI calls Marlin
in-process. The host assembles the listener, TLS, authorization and graceful
shutdown. The package supplies the service, versioned schema and generated
Rust bindings.

| Boundary | Responsibility |
|----------+----------------|
| GPUI and other application clients | Submit Session messages, receive events, resume from an event cursor, and request cancellation. GPUI owns rendering and its local view state. |
| Marlin's Rust gRPC service | Authenticate and translate the wire requests into existing Session and Runtime operations. The journal owns committed messages and event order. |
| =tao3k/weaver= | Supply model routing through its existing integration. Weaver is the implementation owner for the planned A2A and Client ACP adapters. |

Native desktop and mobile apps use the same unary and server-streaming RPCs
as service clients. A browser deployment can expose
gRPC-Web from a trusted origin, forwarding authorization, deadlines,
cancellation and terminal status. If an HTTP/JSON endpoint is needed, it can
project the same Session operations and recovery semantics. GPUI, gRPC-Web
deployment and an HTTP/JSON endpoint are design scope here. The repository
currently supplies the gRPC service and generated client.
[[https://github.com/grpc/grpc-web][gRPC-Web transport]]

[[https://github.com/tao3k/weaver/blob/3242a3ad123ae90eb6250885a09425fec304c19f/docs/10-19-llm-gateway/17-policy-continuation/17.04-protocol-admission-and-identity.org][Weaver protocol inventory]]

The isolated local Weaver candidate at =8ae57a3= calls a separate Turso-backed
Marlin App Server. Its client pin =88c3f9ce= and the current host use identical
=app_server.proto= bytes. The A2A gRPC case submits, reconnects, refuses a
conflicting retry and cancels with one Marlin dispatch. Two ACP JSON-RPC
cases exercise Session creation, resume, foreign Session refusal and live
cancellation. The restart case also recovers the original cancellation
receipt and records two dispatches from the original process, with zero
from the new process. The host's =cancelled= fixture mode returns the
normal cancellation response. The =cancel-response-lost= mode holds it
after the journal commit for the Marlin restart test. These cases use fixture
identities and provisioned Sessions. Production deployment and authorization
remain open.

| Operation | Existing Marlin behavior | Weaver work |
|-----------+--------------------------+-------------|
| Submit or retry | =StartSessionTurn= consumes a stable submission ID, text and previous turn ordinal within the authorized Session. | Resolve the authenticated operation to the original submission before retry. Bind A2A task and ACP session identities to the authorized Marlin scope. |
| Reconnect | =GetSessionSummary= discovers the latest turn. =GetSessionTurnStatus= reads a specified turn. =WatchSessionTurn= reads after the applied per-turn cursor. | A2A subscription opens with a task snapshot. ACP v1 =session/resume= restores the session without history replay. ACP =session/load=, if advertised, replays the conversation. These external behaviors need their own projections. |
| Create an ACP session | =OpenSession= delegates creation or reopening to the host's authorized Session resolver. | =session/new= needs a new host-provisioned Marlin Session and a unique ACP ID. Workspace and MCP access require explicit admission. |

Preserve an uncertain provider outcome even when local retirement completes. |

Weaver needs to persist the authorized operation, its Marlin Session binding
and the original submission tuple before sending it. An A2A task can then
survive a lost start response. A subsequent request resolves the task in the
authenticated scope, retries the original tuple when necessary, and reads
committed events from the same turn. An ACP JSON-RPC request ID correlates the
response on a connection. The ACP session binding and an in-flight prompt
need their own recovery rules when a client reconnects.

supplies the v1 connection, request handlers and notifications. Weaver owns
ACP identity and authorization. The Marlin host owns Session provisioning and
Runtime attachment.

** Cargo feature boundaries

The request path starts at the external client. The client sends
=marlin.app.v1= messages to App Server over gRPC. App Server translates them
into the Rust Session and Runtime operations. =marlin-agent-protocol= owns
shared in-process types and ports that the server uses internally. The
client contract comes from =app_server.proto=.

| Consumer | Cargo feature boundary |
|----------+------------------------|
| Rust desktop or mobile application | Set ~default-features = false~ and ~features = ["grpc"]~ on =marlin-agent-ui=. UI uses App Server's =client= feature and exposes its generated Rust client and descriptor. |
| Rust App Server host | Enable App Server's =grpc= or Agent CORE's =app-server=. The host build includes the service and the existing Session and Runtime adapters. |
| Local TUI and embedded UI | The default =scheme-ui= feature enables Scheme projection. =linked-ui= selects the linked projection path. |
| Web, Swift and Kotlin applications | Generate platform bindings from the same schema or descriptor in the application repository. |
| Weaver | Use App Server's =client= feature to map A2A and ACP operations to Marlin Sessions. |

The client-only dependency graph contains the generated client, Protobuf
types and HTTP/2 channel. CI checks that it excludes Gerbil Scheme and the
Marlin Runtime, Session, storage and internal protocol crates. The Rust
generator derives the descriptor and bindings from =app_server.proto= for
both client and host builds.

A local Cargo project outside the Marlin workspace built the UI client with
only =grpc= enabled. Its generated descriptor matched the host build byte for
byte with SHA-256
=0b4adb4bd86e7eb491ac8e3917154a2a13783e23b4667e86bb1a2bd4f76c6904=.
Over HTTP/2 it submitted a turn to a separate Turso-backed App Server,
received a checkpoint, retried the same submission, resumed from the
checkpoint cursor and read back the cancellation receipt. The host recorded
one model dispatch. The external client's normal and build dependencies
contained neither Scheme nor Marlin's internal execution and storage crates.

* Capabilities and stateless model stream

| RPC | Behavior |
|-----+----------|
| =GetCapabilities= | Authenticated unary call reporting the active request and output limits. |
| =StreamTurn= | Authenticated stateless text turn with ordered user/assistant history ending in a user message. |

The host configures one =ModelEndpoint= and supplies a =ModelStreamingGateway=,
for example the existing =WeaverModelGateway= with its stream output limit set
for the route. The host authorizes each request
for that route. The caller supplies conversation text. Route configuration,
provider credentials and continuation state stay within the host boundary.
The model gateway can use Weaver's LLM client. This package declares Tonic and
Prost directly to generate and serve Marlin's own wire schema. The Cargo lock
shares the Tonic runtime with Marlin telemetry.
[[file:proto/marlin/app/v1/app_server.proto][Protobuf schema]]

The GPUI message path uses the Session RPCs below. =StreamTurn= is the
existing standalone model-stream RPC and carries no Session identity.

The stream emits =Started=, zero or more numbered UTF-8 =TextDelta= messages,
then =Completed= with the chunk and byte totals. Completion means the gateway
completed the text turn. Clients retain the transcript and handle non-OK gRPC
status even after receiving some text. Incomplete or malformed streams fail
with =DATA_LOSS=. Missing authorization is rejected by the host policy.

The service pulls from the existing gateway stream through a one-event relay.
The turn deadline remains active while HTTP/2 waits for client credit.
It bounds the request at
256 KiB and 128 messages, limits streamed text including gateway thinking to
1 MiB, and admits at most 16 active turns across clones of a service instance.
Thinking counts against the budget and stays out of the response. A request
uses the shorter of its gRPC timeout and the server's 120-second ceiling.
Client disconnect or deadline drops the local gateway future or stream and
releases the admission slot. Remote cancellation depends on the provider.
[[https://grpc.io/docs/guides/flow-control/][gRPC flow control]]

* Session and Runtime

The host attaches the =TokioAgentRuntime= Session, project, agent and
=SessionEventStore= through =SessionBinding=. It can expose one fixed binding
or install =AppServer::with_session_lookup= for multiple Sessions. The latter
receives the caller metadata, requested ID and create or existing mode. The
host authorizes each binding and returns the same Runtime owner for a live
Session. The journal's append-only start key arbitrates ownership against
stale writers using the same store.

| RPC | Existing authority | Client behavior |
|-----+--------------------+-----------------|
| =OpenSession= | Host Session resolver and Runtime | Create or reopen a Session under the caller's authorized scope. |
| =StartSessionTurn= | =ConversationJournal::open_controlled= and =start_submission= | Submit user text with a stable submission ID and the last observed turn ordinal. Retry the same inputs to recover the original turn. |
| =GetSessionSummary= | One indexed read of the journal tail and the host's live turn scope | Discover the latest turn and whether it is empty, active, finished or unresolved. |
| =GetSessionTurnStatus= | Indexed reads of the specified turn's header and committed outcome | Read the status of a known turn even after a later turn starts. |
| =WatchSessionTurn= | =SessionEventStore= keyset pages and =SessionEventCursor= | Save the last processed event ID and pass it back as an exclusive cursor after reconnecting. |
| =CancelSessionTurn= | Turn-local Runtime task scope and =RuntimeTaskShutdownReceipt= | Request cancellation and inspect local retirement alongside the committed Session outcome. |
| =GetSessionTurnCancellation= | Journaled Runtime observation and committed turn outcome | Read cancellation evidence by turn after reconnect or restart. |

Start commits the existing journal record before dispatch. The Runtime owns the
task independently of the connection. It replays completed history, persists
text and thinking using the journal's checkpoint operations and commits a
completion, pre-dispatch refusal or uncertainty. Watch returns committed text
and outcomes from the original records. Thinking and provider continuation
stay within the host. The local watch channel signals a commit or task exit.
The journal supplies event data and order. Slow or disconnected observers leave
execution independent of their receive rate.

A GUI resumes from the last event it processed. A delivered event whose cursor
was lost may be delivered again. A cursor must resolve to a committed record in
the requested turn. Replaying from the committed terminal cursor yields an
empty suffix. The client keeps its turn reference across reconnects. Retrying
a committed submission returns its original turn even when the client's
ordinal is stale. A new submission still requires the current ordinal. The service uses one
local turn scope per binding and retains its cancellation receipt source
until the next turn. Journal events persist according to the host's selected
store. A process restart can replay committed records. Recovering an
unfinished provider call after restart needs provider-specific reconciliation.

Cancellation drops the local model future or stream, records uncertainty and
waits for local task retirement. A provider completion selected before
cancellation may still commit. A Runtime wait timeout reports the remaining
task count. Local retirement leaves provider effects unknown when the gateway
has no remote stop receipt. The Session blocks new work on unresolved outcomes.

=dev/quint/app-server-turn.qnt= models journal commit, acknowledgement, replay,
cancellation racing a selected completion, write failure and local retirement.
Run =just app-server-model-gate=. The HTTP/2 test checks the same lifecycle
through the generated client, the existing journal and the Tokio runtime. It
uses the in-memory session store and a deterministic gateway.

* Application message walkthrough
:PROPERTIES:
:CUSTOM_ID: gpui-message-walkthrough
:END:

This example uses the current =marlin.app.v1= gRPC messages. The loopback
HTTP/2 test exercises send, watch, reconnect and cancel. GPUI illustrates
the same client behavior available to mobile and other native applications.
The client opens an authenticated channel to the host, calls
=GetCapabilities=, and uses the returned =session_id= to address the host's
existing Session. A missing =session_id= means the endpoint has no Session
binding. =GetCapabilities= does not provide a transcript or latest ordinal.
The example starts from a known empty Session. The Session summary
below covers opening an existing Session without saved client state.

** Send a draft

The user writes a message and presses Send. GPUI saves a new submission ID
with the draft and its original =after_turn= while the request is pending.
=after_turn= is the last observed turn ordinal, with zero
for an empty Session. The request carries user text only. The host chooses the
route and assembles model history from Session records.

#+begin_example
StartSessionTurn { session_id: "gui-session", user_text: "请开始",
                   after_turn: 0, submission_id: "gui-send-1" }
               -> { turn: { session_id: "gui-session", ordinal: 1 } }
#+end_example

The Session commits its start record before model dispatch. A successful
response lets GPUI associate the draft with the returned turn and advance its
known ordinal. A refusal leaves the draft available to edit or send later.
=ABORTED= can indicate concurrent admission, and =FAILED_PRECONDITION= can
indicate an active or unresolved turn or a stale ordinal. GPUI must preserve
the draft on either result. If the response is lost, show that admission is
unknown and retain the draft. Reconnect and retry the exact request. A
committed submission returns its original turn. =ALREADY_EXISTS= signals
that the ID belongs to different input.

** Receive events and advance the cursor

Open =WatchSessionTurn= for the returned reference. Omit =after_event_id= for
a fresh transcript for this turn. Each server message carries an =event_id=
and one visible event. GPUI routes it to the view for that turn.

| Event | Client projection |
|-------+-------------------|
| =Started= | Mark the turn as started and reuse the user row associated with the start response. The event carries no user text. |
| =TextCheckpoint= | Append its UTF-8 text to the assistant row for the turn. |
| =Outcome= | Record the committed outcome and stop following that turn. |

=REJECTED_BEFORE_DISPATCH= reports a committed refusal before model
dispatch. GPUI can show the refusal alongside the admitted user message.

Treat event IDs as opaque. The Session can persist records that the wire
stream filters out, including thinking checkpoints. Apply visible events in
delivery order and ignore duplicates by turn reference and event ID. When
saving the view for restart, persist the applied projection and its last
applied cursor together. Advancing the cursor upon network receipt can skip
text the GUI has yet to apply. Any late callback from a replaced watch should
be discarded by the client before it updates the view.

** Reconnect and request cancellation

After GPUI applies =第一段=, let =c1= stand for that event's actual ID. The
connection drops and the host commits =第二段=. GPUI reconnects with the same
turn reference and supplies =after_event_id = c1=. The server sends the
committed suffix beginning with =第二段=. Connection loss changes the GUI's
observation state. The Runtime can continue executing while GPUI reconnects.

#+begin_example
WatchSessionTurn { turn: { session_id: "gui-session", ordinal: 1 }, after_event_id: c1 }
               -> { event_id: c2, text_checkpoint: { text: "第二段" } }
#+end_example

If GPUI has the turn reference but no saved view, replay from the beginning
of the turn. An invalid cursor requires rebuilding that turn's projection
from a known position. An empty stream after a saved terminal cursor means
there is no later event to apply. Stream closure before GPUI sees a terminal
event leaves the turn outcome unconfirmed in the view.

When the user presses Stop, send =CancelSessionTurn= for the same turn on a
unary call. The watch can continue receiving committed events while GPUI shows
that it is waiting for the cancellation result. The HTTP/2 fixture observes
this response shape. The actual event IDs come from the server.

#+begin_example
CancelSessionTurn { turn: { session_id: "gui-session", ordinal: 1 } }
                -> { turn: { session_id: "gui-session", ordinal: 1 },
                     runtime: { completed: true, cancellation_requested: true,
                                tracker_closed: true, remaining_tasks: 0, ... },
                     outcome: SESSION_TURN_OUTCOME_REMOTE_UNCERTAIN }
#+end_example

| Observation | What GPUI can display |
|-------------+-----------------------|
| =runtime.completed= is true and =remaining_tasks= is zero | The local task has retired. |
| =outcome= is =REMOTE_UNCERTAIN= | The provider's final state is unknown. Keep the committed partial text. |
| =outcome= is =COMPLETED= | The turn completed. Read any missing text and terminal event through the watch. |
| =runtime.completed= is false and =outcome= is =UNSPECIFIED= | Local retirement was unconfirmed when the RPC responded. Continue observing the Session. =timeout_ms= reports the wait budget. |
| No receipt arrives, or the server no longer has that turn's local scope | Local retirement evidence is unavailable to the GUI. A watch may still recover the journal outcome. |

=cancellation_requested= describes the recorded Runtime operation. Concurrent
Stop calls share that operation, and a retry reuses a completed receipt.
The unary receipt
updates local retirement information. Only an applied stream event advances
the watch cursor. Either message can arrive first. If a journal write fails,
the current cancel RPC can return an error without its Runtime receipt. The
proposed readback contract below keeps these observations recoverable.

The server owns the Session and Runtime state throughout this flow. GPUI owns
the draft, projection and applied cursor. An external application can use the
same RPCs over HTTP/2. The local Weaver candidates use these Session
operations for Marlin-backed A2A and ACP requests.

** User reports that inform the design

- A Codex Desktop report describes a duplicate turn after reconnect, and a
  direct App Server reproduction reports that completing between a history
  read and live subscription can hide the final answer. These motivate separate
  submission recovery and journal replay. [[https://github.com/openai/codex/issues/35203][Codex #35203]] ·
  [[https://github.com/openai/codex/issues/47124][Codex #47124]]
- A Codex user measured a 23 MB resume response with generated images that
  exceeded their client's frame limit. A Claude Code user reported that a
  Session ID emitted during resume could not be used as the next resume target.
  These motivate bounded recovery responses and a stable Session identity.
  [[https://github.com/openai/codex/issues/40362][Codex #40362]] ·
  [[https://github.com/anthropics/claude-code/issues/58760][Claude Code #58760]]
- A Codex user reported a stalled turn after disconnect during tool execution.
  A Claude Code report describes active-turn input that was processed but
  absent from history after resume. These motivate explicit ownership of
  pending work and an admission receipt backed by the journal.
  [[https://github.com/openai/codex/issues/40306][Codex #40306]] ·
  [[https://github.com/anthropics/claude-code/issues/41230][Claude Code #41230]]
- A Codex queue integration reported that the acknowledgement had the same
  meaning to the sender whether automatic dispatch could proceed or was
  paused after interruption. This motivates reporting admission and dispatch
  eligibility separately whenever Marlin exposes a queue.
  [[https://github.com/openai/codex/issues/56914][Codex #56914]]

The five cited Codex issues were open when checked on 2026-11-13. They
describe specific releases and reproductions. The Marlin requirements below
are design inferences from those failures.

** Recover a send whose response was lost

The GUI records a client-generated submission ID and its draft before sending.
The Session ID stays stable across connections. The submission ID identifies
one user action and is scoped to the host's authorized project and Session.
The turn reference
identifies admitted execution. The event cursor identifies an exclusive
position in that turn's committed stream. Connection IDs and provider call
IDs are internal to their respective owners.

=StartSessionTurn= requires a submission ID of 1–128 ASCII letters, digits,
hyphens or underscores. The Session journal atomically commits the existing
start record and a submission record keyed by project, Session and ID. The
submission record points to the original turn. The start record retains the
exact text and its ordinal determines the admitted =after_turn=. A retry
reads these committed records before it checks admission for new work.
If two Runtime owners attempt the same admission against one journal,
only the owner whose transaction commits can dispatch. The other owner can
recover the same turn and read its committed events and receipts. Live
cancellation still requires the Runtime owner of the turn.

| Observation | Server result | GUI behavior |
|-------------+---------------+--------------|
| Same ID and same original input | Return the original turn reference. | Attach to that turn and keep the existing transcript. |
| Same ID and changed input | Return =ALREADY_EXISTS=. | Keep the draft. A new user send gets a new ID. |
| Different ID while the Session is busy | Refuse admission. | Keep the unsent draft. |
| Admission response unavailable | Retry the exact request with the same ID. | Show that the send is being checked. |

For this contract, a busy Session refuses new submissions. If queued input
is added later, the Session must expose queue admission, dispatch eligibility
and the typed reason for a pause. A queued draft becomes an admitted turn only
when its own start record commits.

The equality check binds the exact user text and original =after_turn= to the
submission. A retry keeps these fields even if the view has advanced. If a
start is committed and the owner disappears before the dispatch outcome can be
established, recover the original turn reference with an unresolved state.
The provider may already have seen the request. Recovery cannot automatically
dispatch it again. Turn-local ownership and journal commits govern one
admission; remote side effects need provider evidence.

** Reopen a Session without rebuilding the whole view

=GetSessionSummary= reads the latest conversation event header for the
authorized Session. The lookup seeks the existing journal key
range and reads one header. The response contains the latest turn, its
journal position, and a typed recovery state. Admission that holds the local
turn lock can return =ABORTED= so the caller can retry the read. A finished
turn has a committed finish record. An uncertain terminal record or an
unfinished turn without a live local owner is unresolved.

A fresh GUI uses the returned turn with =WatchSessionTurn= from the start.
A restoring GUI uses the last cursor whose visible event it applied and
saved. The summary position describes journal state and can include a
checkpoint that the visible stream skips.

=GetSessionTurnStatus= seeks the indexed range of one specified turn and reads
its outcome when committed. A missing turn returns =NOT_FOUND=. The returned
journal position is informational. Replay resumes from the applied cursor.

Keep =WatchSessionTurn= as the ordered suffix of the same journal. A terminal
event committed during attach appears in the replay suffix whenever the client
has yet to apply it. The client deduplicates by turn reference and event ID.
After any transport interruption it can recover the same suffix. A watch
deadline, connection close or silent observer leaves the turn's outcome to the
Session owner. The durable store and the live Runtime independently determine
whether a turn is terminal, still executing or unresolved.

Each Session RPC has one deadline covering host lookup and journal access.
For a watch, that deadline also covers replay and waiting for new events.
When a Start response times out after Runtime admission, retry with the same
submission ID to recover the original turn.

The App Server admits up to 16 concurrent Session watches. An additional
watch receives =RESOURCE_EXHAUSTED= and can retry from its applied cursor.
Each watch reads one turn at a time, with up to 16 records and 8 MiB of
stored event bodies per page. The storage read returns the ordered prefix
that fits. Replay resumes from that prefix's last cursor, including when a
page ends on the byte limit. If one event exceeds the entire budget, the
watch returns =RESOURCE_EXHAUSTED= when it reaches that event. These byte
limits apply to stored bodies returned by the storage query. Turso may
read candidate payload pages internally to evaluate their lengths.
The watch queues at most one event for its HTTP/2 response. The replay task
releases its page and slot on deadline or disconnect, including while the
HTTP/2 stream has no credit.
Summary, status, and cancellation do not consume watch slots.
A large transcript or artifact is fetched on demand through its authorized
owner. Model input construction has its own budget. If a Start request ends
while reading history, its Runtime admission task drops the read and
releases the Session. Once the atomic journal write starts, the Runtime
finishes admission so a retry can recover the original turn. Admission reads
history across turns in pages of at most 16 records and 8 MiB of stored
event bodies. An oversized record or history beyond the model input budget
returns =RESOURCE_EXHAUSTED= before dispatch.
The GUI can keep the draft and continue reading the committed results.

** Recover cancellation evidence

Keep observation, cancellation and a new submission as separate actions. The
GUI shows that cancellation was requested, then reports local task retirement,
its wait timeout or missing evidence from a typed Runtime receipt. A completion
that wins the race remains the committed turn outcome. If the provider supplies
no stop evidence, display that uncertainty alongside local retirement. If the
Session write fails, surface the journal error independently of the Runtime
result so a locally retired task can still require Session reconciliation.

=CancelSessionTurn= records the Runtime observation before returning it.
Once the Session Runtime admits the cancellation, recording continues if the
RPC times out or the client disconnects. A repeated Stop joins an in-progress
operation or returns its completed receipt. If the local scope has been lost,
the same request returns persisted evidence when available. The client can
also reconnect and read the receipt by turn.
=GetSessionTurnCancellation= reads the strongest recorded observation for
the authorized turn, together with the committed outcome if present. The
journal retains the first observation at each strength. Completed local
retirement takes precedence over an incomplete observation. Stop replies
with the retained observation when a repeat write finds one. A process
restart preserves those records. When no observation was recorded, the
read returns =unavailable= evidence. Provider effects remain governed by
the committed Session outcome. Tool-call recovery is outside the current
text-turn contract.

** Session acceptance scenarios

| Scenario | Required observation |
|----------+----------------------|
| Start committed, response dropped, two clients retry or send concurrently | The original sender recovers its exact turn by ID. The other draft stays unadmitted. The gateway receives one dispatch. |
| Same submission ID with edited text, then retry after the turn is superseded | The edited payload gets a typed conflict. The original payload resolves to the original turn. |
| Completion races attach on both sides of a journal read | Applying the replay suffix yields the complete visible text and exactly one outcome. Replaying from its terminal cursor yields an empty suffix. |
| Lost local cursor, stale listing index and large prior history | Direct Session lookup still works. Bounded pages restore the view. A second Session's cancel and summary calls stay responsive while replay is backpressured. |
| Cancellation races completion, journal write failure or provider stop timeout | The GUI can distinguish the committed outcome, journal error, Runtime retirement and remote stop evidence. Retrying after a later turn recovers recorded evidence or an explicit unavailable receipt. |
| Host restarts with a committed start and uncertain provider dispatch | The original identity and last committed text survive. Status shows unresolved dispatch and the gateway sees no automatic resubmission. |

Quint covers lost start responses, conflicting input, competing submissions,
and restart with a committed checkpoint and no live turn owner. The real
HTTP/2 fixture pauses the start after its atomic commit,
drops the caller, then verifies that retry returns the original turn and that
changed input conflicts. It releases the original owner and checks one
gateway dispatch. A second HTTP/2 test uses a temporary Turso database. It
drops the start response after commit, waits for the first committed text
checkpoint, kills the server process, then opens the same database from a
new server process. It checks the original turn, =ALREADY_EXISTS= for changed
text, replay of the original checkpoint, and one gateway dispatch across
both processes. The replay reports that the unfinished turn has no live owner.
The concurrent admission fixture opens two HTTP/2 listeners with independent
Runtime owners over the same Turso storage. Both reach the start transaction
before either writes. One dispatches, both return the same turn, and the
second can read the first owner's cancellation receipt once committed.
A separate Turso HTTP/2 test pauses Stop after Turso commits the local
retirement receipt and drops the outstanding response. A new server process
reads the same receipt by turn and returns it on a repeated Stop. The
watch resumed from the pre-restart checkpoint yields the uncertain outcome
once. The gateway sees one dispatch in total.
The same Turso fixture can refuse the terminal event write while accepting
the retirement record. Stop returns the storage error. After restarting, the
client reads that retirement record and sees an unresolved Session without
a committed outcome. Retrying the submission returns the original turn.
The Turso HTTP/2 watch fixture holds 16 observers at zero stream credit,
checks summary and cancellation for another Session, and opens a new watch
after one deadline elapses. It then reconnects to read the history in order
from a committed cursor across byte-bounded pages and rejects an oversized
record in the next turn. Quint checks the same
admission and cancellation ordering with three observers and two slots.

* Build and embed

Use the repository's protobuf toolchain (=protoc=). Generated Rust bindings
and =marlin-app-v1.bin= are generated in the same Cargo build step from the
one =app_server.proto= source. Rust exposes the descriptor as
=marlin_agent_app_server::v1::FILE_DESCRIPTOR_SET=. Distribute that schema
or its descriptor to downstream code generators for each platform. Client
projects own their UI and language-specific generated bindings. A native app
can use its platform's gRPC plugin with the descriptor as the input schema.
For example, ~protoc --descriptor_set_in=marlin-app-v1.bin~ can supply the
schema to an installed language generator for =marlin/app/v1/app_server.proto=.
Build and test with =cargo test --locked -p marlin-agent-app-server --features grpc=.

Run the Rust UI client check with
~cargo test --locked -p marlin-agent-ui --no-default-features --features grpc --test grpc_client~.

Run the persistent restart test alone with
~cargo test --locked -p marlin-agent-app-server --features grpc --test session turso_http2_recovers_lost_submission_after_process_restart -- --exact~.

#+begin_src rust
let session = marlin_agent_app_server::SessionBinding::new(store, project, agent, runtime)?;
let service = marlin_agent_app_server::AppServer::new(endpoint, gateway, authorize)?
    .with_session(session);

    .add_service(service.into_service())
    .serve_with_shutdown(bind_addr, shutdown)
    .await?;

The host supplies the typed endpoint, shared gateway, metadata authorization
callback, bind address and shutdown future. Configure TLS on the server or at
the trusted gateway for external deployments. An embedding binary depends on
Tonic to configure its transport. The loopback integration test uses a fixture
gateway and the generated client over real HTTP/2.
