* Test ownership

| Layer | Unique responsibility |
|-------+-----------------------|
| Scheme unit/property tests | Catalogs, ranking, keymaps, preview/cancel, folding, layout and package semantics |
| Scheme test window | Package assertions against actual mapped rows, cursor and hit regions |
| Rust unit/property tests | Typed admission, conversion, bounds, generic mapping and cache mechanics |
| Linked ABI tests | Rooted values, compiled closure, successor admission and native lifecycle |
| PTY | First input, mouse/wheel delivery, streaming, resize, suspension and restoration |
| Performance gates | Fixed workload latency, tails, retention and source-free linked launch |

Do not duplicate labels, command lists, theme values or fold symbols in Rust
when Scheme already owns those assertions. Preserve native rejection and PTY
coverage that observes a different boundary. No dead-code allowance is an
acceptable substitute for removing a retired path.

* Requirements and models

| Requirement | Qualification responsibility |

| MAR-TUI-R04 | Session replay, cursor identity and duplicate prevention |
| MAR-TUI-R05 | Source-matched debug/release startup and interaction measurements |
| MAR-TUI-R06 | Unicode, paste, cursor and resize invariants |

The [[file:../../../dev/sysml/tui-architecture.sysml][architecture]], [[file:../../../dev/sysml/tui-declarative-engine.sysml][engine]] and [[file:../../../dev/sysml/tui-lifecycle.sysml][lifecycle]] models own structural requirements.
Executable behavior/property tests own their implementation checks. Existing
Quint and Runtime models retain their declared scope; a UI snapshot does not
prove concurrency or external effect atomicity.

* Standard acceptance sequence

Use the project environment, default Rust target and native package manager.
=GERBIL_BUILD_CORES= defaults in the project environment; tests retain their
existing heap, action, idle and aggregate limits.

1. Rebuild linked development dependencies through standard Gerbil pkg tools.
2. For Yuanxu resolution changes, run its windows, role-context, effect-support,
   publication and testing-source-admission suites serially.
3. Run Core =just test-build-input-context-mutations <artifact-dir>=. All four
   faults must be rejected by the intended assertions, with normal controls
   passing before/after and source digests unchanged. Compiler failures and
   timeouts do not count as rejected mutations.
4. Run Lab's =build-qualification-library= prerequisite and
   =t/yanxu/modules/services/opentofu/deployment-test.ss= with its original
   budgets. Projection must construct zero business scopes.
5. Run =just scheme-build=, =just scheme-package-gate= and
   =just scheme-ui-package-gate= in Marlin.
6. Run Yuanxu's =t/program-activation-test.ss= through its standard test entry.
   It executes a linked program with no fixture library on the load path and
   checks nested startup dependencies, delayed activation, once-only execution
   and stable refusal. Build the default debug executable with
   =just tui-aot-debug=, which consumes the compiled =ui-tui= Module through
   its Interface. Run the real PTY tests, including the independent package,
   first-arrow regression and normal process exit.
7. Run =just tui-ui-mapping-bench= and =just tui-performance-bench= on the fixed
   source cohort, including release without the Gerbil package tree.

Require natural completion and the expected harness markers. Gerbil can exit
zero after =ERROR CASE= or =ERROR HARNESS=; those are failures. Raw logs stay in
local/CI artifacts, not version control. A failed gate blocks its acceptance
claim while independent work can continue.

* Independent package criterion

The [[file:../../../crates/marlin-agent-tui/tests/fixtures/ui-extension/fixture.ss][ui-extension fixture]] declares a notes Buffer, open-notes command and M-z key.
Its Scheme scenario checks publication isolation, painting, resize and hit
bounds. Rust supplies the existing production mapper; it has no handler for
those identities. The configured package must also open through its key in a
real PTY and restore the terminal on quit.

A package build alone is insufficient. Dynamic VM loading and the distribution
linked closure require separate evidence; static distribution may require
relinking, without requiring changes to Rust source.

* Role-bound frame qualification — 2026-11-16

This development cohort uses Yuanxu =7bae6b5a=, POO =ccdb3db= and the
linked Lab checkout. The standard Scheme build and workbench suite passed.
The Rust library suites passed 253 tests with ten ignored. The default
linked PTY suite passed 17 tests with 37 ignored.

The independently built package declares its own Buffer, command, key,
element tree, row values and method bundle. The Scheme window tested the
rendered output at two dimensions and dispatched the actual hit row. In a
separate terminal test, M-z opened the Buffer; clicking its first row moved
focus through the package's method, and Return opened M-x. Both terminal
tests restored terminal state on normal exit. The Debug example configuration
reached its first frame in 282 ms on this host.

The 30 two-frame debug window samples measured 23.6 ms at the median and
87.9 ms at P95, including Scheme assertions and excluding scenario creation.
These samples are not a fresh executable launch measurement.

* Pinned Darwin startup qualification — 2026-11-20

Marlin =765f1abf=, Lab =5702335b= and Yuanxu =359a85c6= were built from a
clean source checkout with the locked Gerbil packages and standard Cargo
commands. The arm64 Debug and Release executable SHA-256 prefixes are
=5450c8998987= and =74463df9fd6d=. The benchmark compiled its Rust test
drivers first and restored the product paths with =cargo build=. All twelve
paired PTY runs per profile reached the workbench and exited within the
original limits. Other compiler activity was observed on the host.

| Profile | Fresh-copy workbench median / max | Same-file workbench median | Fresh-copy time to Rust entry median |
|---------+-----------------------------------+----------------------------+--------------------------------------|
| Debug | 2.157 / 4.178 s | 72 ms | 1.810 s |
| Release | 1.767 / 2.262 s | 68 ms | 1.389 s |

The Release first-arrow test, extension with only compiled plugin artifacts,
and Worktrunk without a Gerbil installation passed. The extension action
registered once and could be called repeatedly. Its three first-action
measurements ranged from 19.7 to 868.7 ms. The first M-x arrow after the first
frame in ten new Release processes had a maximum latency of 20.9 ms.
Fresh-copy startup remains above the subsecond target in this cohort.

On the same Release executable, the pre-UI time to Rust entry had medians of
15 ms for the existing file, 15 ms by symlink, 394 ms by hardlink, 1.325 s for
a new copy and 1.354 s for a clone-requested copy. Direct and linked paths
resolved to the existing inode. Both copy modes used new inodes. These
controls identify a first-execution cost that depends on file identity and
access path. The system trace did not identify the specific OS subsystem.

The same Release also completed eight interleaved PTY trials per case with a
shared experimental launcher. End-to-end workbench medians were 2.047 s with
direct execution, 1.187 s including a sequential read and 1.921 s including a
230 ms wait. Other compiler activity was observed. The sequential-read case
improved the median in this diagnostic and its fastest sample was 1.037 s.
That result does not qualify a subsecond product startup.
